## 2. 建议的统一后端契约

主链路：

`冻结本轮证据 → 生成 → 解析与安全规范化 → 精确解析引用 → 完整性校验 → 原子保存 → 返回最终正文`

### 2.1 一个公共解析/规范化模块

以 `internal/citation` 为公共模块边界，和 #214 的抽取方向对齐；不擅自合并该 PR，也不把“每条引用限量”捆绑成此次修复的前置条件。

统一识别英文 `[9]`、中文 `【9】`、全角 `［９］` 等明确支持的形式，规范输出为 `[9]`。团队 `[P9]` 使用独立命名空间，不能被转成消息引用。

按 Markdown 文本节点或源位置处理，保留正文排版，不重新序列化整篇文章。代码块、行内代码、链接、转义文字不作引用改写。`[1,2]`、`[1-3]` 等未定义形式不得部分匹配后假装成功，第一批应报格式错误并进入修复；是否支持展开另行明确。

不能仅用“编号大于最大值”认定它是普通文字。对生成总结约定数字方括号为引用语法；确实需要普通方括号数字时可转义。无法可靠区分的输出进入一次明确的格式修复，不盲目猜测、替换年份或制造引用。用户手工编辑不自动调用模型重写，冲突直接返回可定位的错误。

### 2.2 引用必须绑定本轮真实证据

复用已有 Agent evidence/manifest 能力，为 Workflow 提供同契约的适配器，冻结“实际展示给模型的编号 → 消息或历史版本”映射。编号不应在 Map、Reduce、保存阶段按不同消息排序重建。

消息键包含空间、频道及类型、消息标识；引用个人/团队总结时固定到源版本。保存生成轮次与必要的映射快照，遵循既有权限和保留策略，不无限存储完整聊天正文。

只认服务器提供且授权的映射，不信任模型自报的 sender、消息 ID 或引用详情。范围内的编号仍可能不存在，必须验证精确集合；允许只引用 `[2][7]`，不要求正文必须从 `[1]` 开始。

仅措辞优化可继承明确父版本的冻结证据；新增取证使用本轮映射及显式合并规则，不能回退到“会话最新一轮”猜映射。相同正文出现在不同群里不是同一条证据，不能只按正文相同合并来源。

### 2.3 新增“引用完整性提交检查”

该检查与既有 finish gate 分离：质量/覆盖结果仍按原规则披露；引用结构损坏不能成为可发布的成功版本。

检查至少包括：

1. 所有被认定为引用的标记均能解析，且映射到授权证据；零、负数、溢出、重复编号指向不同来源均拒绝。
2. 正文的有效引用集合与本次展示引用条目一致。完整 evidence pool 可以含未引用条目，不能混淆这两种集合。
3. 中文与英文混用也全量检查，不能因为一个 `[1]` 有效就漏掉 `【999】`。
4. 对有聊天依据的事实总结，不能接受“正文含引用但解析结果为空”，也不能接受完全没有来源引用的事实总结。澄清、无数据、普通对话须以可信流程状态豁免，不仅凭模型自行声称无数据。
5. 引用真实存在不等于其支持相邻结论；逐条事实依据/语义覆盖需要额外检查，不能宣称正则已保证内容正确。第一批只强保证语法、映射、权限、保存一致性，事实质量另行验收。

顺序上必须先发现并报告非法引用，再做有明确定义的重复标记消除和格式整理。不能先调用 `stripOrphanCitations` 把错误删掉，再据此认为校验通过。若未来接入 #214 的限量，限量后重建展示引用条目，并再校验一次。

## 3. 失败、接入与持久化

### 有限修复，不假成功

安全括号规范化由后端确定性完成，不花一次额外模型调用。无法解析时，生成流程最多追加一次引用修复请求，携带违规位置、原因和允许引用的证据；仍失败则返回结构化错误，不循环重试、不把失败输出标成 completed。

首次生成保留任务和失败信息供重试；优化或定时生成保留上一有效版本。原始失败正文可按现有受控诊断策略保留，但不能成为当前正式总结。手动编辑/恢复不调用模型。

这是待确认的行为调整：引用完整性失败阻止发布，但不是把 #205 的所有 PARTIAL/FAILED 质量判决重新改成硬阻断。

### 全入口覆盖

| 入口 | 应用位置与要求 |
| --- | --- |
| Agent 预览、修订及保存 | 预览前规范化与检查，保存时按同一轮/明确父版本证据再验证。 |
| 模板 Workflow 首次生成 | 单 Map、Map/Reduce 最终输出均走公共处理；旧写入路径也不能绕过。 |

| 手工编辑、恢复、复制等写入 | 不生成新证据；校验目标版本与证据一致性，历史脏数据不静默晋升为已验证结果。 |

范围不要求本次顺带完成全部统一版本开发，但所有已存在的成功写入入口必须覆盖同一引用契约。新开发入口也必须依赖该契约，不能留第二套宽松校验。

正文、展示引用、证据绑定及版本/成功状态按现有事务边界一起保存。提交之后再发布规范化后的最终快照并结束流，不能让未修正的流式正文与数据库正文长期不一致。

复用现有 `snapshot`/`done` 和结果读取接口；[Hub](/home/mlamp/worktrees/summary-versioning-backend/internal/streaming/hub.go:118) 已能替换快照。需要接上最终正文，并测试慢客户端、断线重连、旧 run 延迟事件；事件失败时以已提交的结果读取为准。不改前端布局、模板交互和引用样式，不在前端补造来源。

日志仅记录 run/task、解析数、规范化数、引用数、失败类型和有限修复次数；不默认记录完整聊天、提示词或密钥。

## 4. 实施顺序与验收

建议按三个可验证阶段实施，预计 3–5 个工作日；这是基于现有代码的规划估算，不含范围新增或外部模型长时间不可用：

1. 公共解析器、冻结证据契约和单元测试，先用 task 61 正文做离线回归，约 1 个工作日。
2. 所有现存写入入口、有限修复与最终流式快照接入，约 1–2 个工作日。
3. 隔离镜像真实模型回归、并发/失败和权限检查，约 1–2 个工作日。

离线验收覆盖五组：

| 组 | 必测内容 |
| --- | --- |
| 语法 | 英文、中文、全角、混合、重复、稀疏编号、零/负数/溢出、未定义组合写法。 |
| 非引用 | Markdown 链接、代码、转义、普通年份和数字；不篡改非引用内容，歧义不能靠范围猜。 |
| 映射与权限 | 范围内缺号、跨轮次、跨频道同正文、父版本继承、未授权证据、已失效证据。 |
| 写入与状态 | 校验失败无成功版本；定时/优化失败保留旧版本；原子提交、租约失效、并发、重试幂等。 |
| 输出一致性 | 最终流式正文、API 正文、数据库正文及引用一致；断线刷新后仍一致。 |

镜像必须实际覆盖：Agent 首次生成、模板 Workflow 单 Map、模板 Workflow Map/Reduce、继续优化、实际定时执行、多人层级引用。逐项查看真实消息引用跳转，不再用固定 Alpha 文本或只通过 Agent 路径代替整体验收。

最终接受标准：合法异体括号可规范化并正确跳转；无法证实映射的引用不发布；旧版本不受失败生成影响；原有 Octo 界面不变。
